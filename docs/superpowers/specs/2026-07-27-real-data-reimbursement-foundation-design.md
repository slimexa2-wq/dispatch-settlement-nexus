# 祥能真实数据与报销闭环设计

## 目标

本轮只做两件必须做实的事：

1. 用用户提供的真实周度在离职表和企业人员名单替换内部运行环境中的虚构项目、人员、供应商来源与组织归属数据。
2. 将报销从“个人报销单逐张审批”调整为“员工一次录入、系统自动校验、按真实部门自动汇总、财务按部门批次审核、审核后按报销人与金额汇总打款”的完整闭环，并确保微信小程序入口真实可见、可用。

## 总原则

- 一次录入，全程复用；一处更新，自动同步。
- 能由系统确定完成的校验、计算、汇总、查重与状态联动，不交给人重复操作。
- 使用用户提供的真实数据，不脱敏、不编造；数据缺失保持为空并记录来源。
- 内部真实数据与公开演示数据隔离。内部运行默认使用真实数据，公开静态演示继续使用合成数据，避免将真实身份证、电话发布到互联网。
- 组织架构使用可配置组织单元树，不把当前层级写死在业务代码中。

## 真实数据模型

### 来源一：周度在离职数据

来源文件：`祥能人力周度在离职数据统计_20260719.xlsx`

用于建立：

- 经营区域/分公司；
- 项目主档；
- 业务类型；
- 项目在职、自招、供应商人数；
- 本期入职、本期离职、环比和原因说明；
- 项目与分公司的真实归属关系。

汇总行如“22个项目”“合计”等不作为项目主档，仅作为源数据核验信息。

### 来源二：所有企业名单

来源文件：`所有企业名单汇总2026-07-21 17_21_30_2 (6).xls`

用于建立：

- 人员主档；
- 面试企业与项目映射；
- 供应商/人员来源；
- 推荐人；
- 面试、入职、离职状态及日期；
- 所属部门；
- 供应商政策、员工政策、结费政策；
- 紧急联系人信息。

同一身份证优先作为同一人员主档；每一行保留为一次报名/面试/入职业务记录，避免覆盖历史。

## 报销业务闭环

### 员工小程序

- 首页固定显示“我的报销”，不因演示角色映射遗漏而隐藏。
- 新增费用明细、上传付款凭证和发票、保存草稿、提交、查看状态、查看退回原因、修改后重提、查看审核金额和付款状态。
- 所属部门从内部员工当前主任职自动读取，不允许员工自行选择其他部门、项目或供应商。

### 自动校验

系统在提交前自动完成：

- 明细金额为正数；
- 付款金额与申报金额一致；
- 发票金额满足配置规则；
- 付款凭证和发票附件完整；
- 发票代码、号码、金额、日期及文件哈希查重；
- 明细合计与批次合计一致；
- 重复提交幂等校验。

确定重复的发票直接阻止提交；疑似重复才进入人工异常处理。

### 部门批次

员工提交后，系统按组织单元与报销周期自动归入部门批次。部门制单人不重新录入，只处理系统无法确定的异常并确认提交。

部门批次自动生成：

- 部门汇总审核表；
- 费用类型汇总；
- 报销人及金额汇总；
- 报销明细表；
- 付款凭证打印包；
- 发票打印包。

### 财务审核与付款

财务以部门批次为主对象审核，可下钻个人和明细。审核通过后系统生成“报销人、部门、审核通过金额、账户信息、付款状态”的付款汇总表。

出纳可批量登记付款；系统校验实际付款金额与审核金额，自动回写每个人的付款状态和时间。

## 技术边界

- 保留现有 React、Fastify、Prisma、Taro 架构。
- 增加真实数据标准化 JSON 与来源校验报告。
- 公开演示构建不得引用内部真实数据文件。
- 新增报销部门批次聚合服务与导出生成物，不破坏现有个人报销明细模型。
- 所有新增规则先写失败测试，再实现。

## 验收标准

- 内部数据集中不存在“祥能演示一分公司”等虚构组织、项目或人员。
- 真实数据条数、项目数、分公司数、人员数、状态分布可与来源文件对账。
- 小程序首页所有内部员工均能看到“我的报销”，并可完成草稿到付款状态查看。
- 财务能在一张部门汇总表完成审核，并生成报销人与金额付款表。
- 金额一致性、附件完整性、重复发票和合计勾稽由系统自动校验。
- 公开静态演示构建不包含真实身份证、电话和源文件内容。
